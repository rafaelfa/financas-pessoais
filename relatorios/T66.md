# T66 — O schema degrada em vez de rebentar: prova do QA

**Veredicto: PASS nas seis alíneas.** O valor inválido de um filtro cai **só ele**; os cinco
números do URL são os que o Dev colou; a expectativa que mudou na T64 é **deliberada e está
escrita** no teste; e a correção vale pela sonda do chamador cru (a página já normalizava, por isso
os totais do URL são iguais antes e depois).

## 1. A expectativa que mudou na T64 — deliberada, não afrouxamento

**Antes** (T64), o teste dizia:

```ts
it('só o valor `1` é aceite — o resto é recusado, não ignorado', () => {
  expect(transactionFiltersSchema.safeParse({ semCategoria: '0' }).success).toBe(false);
  expect(transactionFiltersSchema.safeParse({ semCategoria: 'true' }).success).toBe(false);
});
```

**Agora**, o mesmo caso chama-se «só o valor `1` vale como filtro; o resto cai sem rebentar o
resto» e assere que `'0'`/`'true'` dão `success: true` com `semCategoria: undefined` — e que `'1'`
continua a valer. A mudança está **comentada no teste** («Muda em relação à T64… com a degradação
por campo (T66), o que acontece é o que se quer de um filtro vindo do URL»).

Não é um teste ajustado para o código novo passar: a asserção ainda pode falhar (se `semCategoria`
aceitasse `'true'`, `parsed.data.semCategoria` não seria `undefined`; se `'1'` deixasse de valer, a
última asserção cai). É uma **mudança de contrato** — «filtro inválido = filtro ausente», a mesma
regra que o `parseAmountFilter` já seguia e que a página já aplicava —, e o preço é que uma
`?semCategoria=true` deixa de dar erro para dar a lista completa. Está declarado, não escondido.

O que **não** mudou: as chaves continuam declaradas (o `strict()` da T64 continua a passar — o
teste do objecto completo está lá e verde), e `semCategoria=1` continua a filtrar.

## 2. Os cinco números do URL — 60 lançamentos, 3 com «mercado»

Cenário próprio (`e2e-t66.medir`, 60 gastos, 3 descrições com «mercado»):

| pedido | total | esperado |
|---|---|---|
| `/transacoes` | **60** | 60 |
| `?search=mercado` | **3** | 3 |
| `?semCategoria=true&search=mercado` | **3** | 3 |
| `?semCategoria=true` | **60** | **60** (não 50) |
| `?limit=abc&search=mercado` | **3** | 3 |

**Todos iguais aos que o Dev colou.** E os critérios 1 e 2 lidos à letra: com `semCategoria=true`
(o valor inválido) o `search` continua a valer (**3**, não 60) e sozinho devolve a **lista completa
(60)**, não os 50 do default — é o `catch` a repor `limit: 50` em vez de a consulta cair para o
`{limit, offset}` do `safeParse` falhado.

## 3. A sonda do chamador cru

```
$ npx tsx probe.ts
{"semCategoria":"true","search":"mercado"} → true {"search":"mercado","limit":50,"offset":0}
{"semCategoria":"0"}                      → true {"limit":50,"offset":0}
{"semCategoria":"1"}                      → true {"semCategoria":"1","limit":50,"offset":0}
{"limit":"abc","search":"mercado"}         → true {"search":"mercado","limit":50,"offset":0}
{"kind":"inventado","status":"pending"}    → true {"status":"pending","limit":50,"offset":0}
{"semCategoria":"1","valor":"100","valorOp":"gt","search":"mercado","limit":"25","offset":"50"}
                                          → true {search, semCategoria:'1', valor:'100', valorOp:'gt', limit:25, offset:50}
```

`success: true` **e** o `search` no resultado — o sintoma que a T66 fecha (antes: `false` e
`{limit:50, offset:0}`, tudo perdido).
