## 5. `FormMessage` — **REPROVA**

O código está como o Dev descreve: `FormField` embrulha o `render` num
`FormFieldContext.Provider value={{ error: fieldState.error?.message }}` e
`FormMessage` lê o contexto e devolve `null` quando o valor é vazio
(`ui/form.tsx:59-69`). Há **8** marcas `<FormMessage />` (não ~13) e todas estão dentro
de um `FormField`: `account-group-dialog.tsx:144,162` e
`receivable-payable-dialog.tsx:218,240,254,281,306,325`.

O problema é a montante: **o resolver lança em vez de devolver erros**, portanto o
`fieldState.error` nunca é preenchido e não aparece mensagem nenhuma.

Prova 1 — resolver isolado, com o schema exato do diálogo (Node, versões instaladas):

```
$ node -e "zodResolver(schema)({type:'PAYABLE',description:'',amountInCents:0,dueDate:'2026-11-01'},{},{})"
THROW [
  { "origin": "string", "code": "too_small", "path": ["description"],
    "message": "A descrição é obrigatória" },
  { "origin": "number", "code": "too_small", "path": ["amountInCents"],
    "message": "O valor deve ser maior que zero" }
]
```

Com o schema do grupo: `THROW [... "message": "O nome é obrigatório" ...]`.

Causa exata: `@hookform/resolvers@3.3.0` faz `if (error.errors != null) return
{values:{}, errors: toNestErrors(...)}; throw error;`. O Zod 4 deixou de expor
`error.errors` (expõe `error.issues`), logo a condição é falsa e o resolver **rejeita a
promessa com o `ZodError`**. O `handleSubmit` do react-hook-form não transforma essa
rejeição em `errors`, e é por isso que não há `onInvalid` nem `fieldState.error`.

Prova 2 — render real do diálogo (harness com esbuild, componentes reais, actions e
`next/navigation` substituídos por stubs; sem base de dados), formulário vazio e
clique em "Criar Conta":

qualquer dos casos, com prova de que o `FormMessage` recebe o erro.

## 5. O `as FieldErrors<…>` — dívida?

Aceito e **não reprova**. É um único cast, no único sítio onde não há alternativa
honesta: `FieldErrors<T>` é um tipo mapeado sobre as chaves do formulário, e o adaptador
constrói o saco de erros a partir de caminhos do Zod em runtime — nenhum tipo estrutural
prova isso sem um genérico por campo, que seria mais código do que o problema. O cast
está comentado com a razão, e cada valor continua a ser `FieldError` real (o que o React
Hook Form lê). Registado como **nota** neste relatório; não justifica tarefa própria. Se
o projeto quiser a regra "zero casts", vai para a T12 com o conjunto todo, não só este.

Duas limitações do adaptador, para ficarem anotadas (nenhuma afeta a T7, ambas com tarefa
dona):

- os erros são indexados por `issue.path.join('.')`, ou seja, chaves planas (`"a.b"`). Os
  dois formulários atuais são planos, por isso funciona; um formulário com objetos
  aninhados esperaria um objeto aninhado em `errors`. Anotar na T12 (junto com o resto da
  limpeza) ou onde o projeto tratar de formulários.
- `values: parsed.data` devolve o que o Zod validou, portanto **descarta** chaves fora do
  schema — é o que continua a comer o `accountIds` do formulário de grupos (T8, já
  aberta). O adaptador não piorou nada: o `@hookform/resolvers` fazia o mesmo.

Complexidade: medida com o ESLint do projeto e uma regra ad hoc,
`pnpm exec eslint src/lib/zod-resolver.ts --rule '{"complexity":["error",1]}'` →
`15:25 error Async arrow function has a complexity of 5. Maximum allowed is 1`. São 5,
como o Dev disse, abaixo do limite de 10.
