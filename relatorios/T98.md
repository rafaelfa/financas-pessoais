# T98 — a falha de rede no formulário de preferências fica muda

Data: 2026-11-22 · Base: `main` @ `31118ee`
Build: `BUILD_ID fcybuCGojuWiXcJ8rVkVY`

## 1. Onde é que a excepção morria (a pergunta do Lead, antes da correção)

Reproduzido com o pedido abortado (`page.route('**/definicoes', … abort('failed'))`) e medido no
browser. **A excepção morre na `await` dentro do callback do `startTransition`:**

```tsx
startTransition(async () => {
  const resultado = await savePreferences({ … });   // ← é aqui que rejeita
  …
});
```

O `startTransition` em si **não é** o culpado: ele acompanha a transição e a rejeição não é por ele
engolida — sobe como *unhandled rejection* e o **error boundary do segmento** apanha-a. O que o
utilizador vê, medido: `document.querySelectorAll('form').length` → **0**, `main.innerText` →
«**Algo falhou ao carregar este ecrã** — A consulta aos teus dados não chegou ao fim…»; sem
`[role="alert"]` e sem toast; a consola com `TypeError: Failed to fetch`. Ou seja: não era só «nada
acontece» — o formulário **desaparecia**.

## 2. A correção

Um `try/catch` **à volta do `await`**, dentro do callback (é o único sítio onde a promessa da Server
Action rejeita e onde a mensagem consegue ir para a página em vez de para o boundary):

```diff
     startTransition(async () => {
+      try {
-      const resultado = await savePreferences({ … });
+        const resultado = await savePreferences({ … });
 
-      if (!resultado.ok) {
-        setErro(resultado.error);
-        return;
-      }
+        if (!resultado.ok) {
+          setErro(resultado.error);
+          return;
+        }
 
-      toast.success('Preferências guardadas.');
+        toast.success('Preferências guardadas.');
+      } catch {
+        setErro('Não consegui ligar ao servidor — as preferências não foram guardadas. Verifica a ligação e tenta outra vez.');
+      }
     });
```

Mensagem em pt-PT, em «não gravou» **e** «tenta outra vez», com o `role="alert"` que já existia. Sem
segundo canal de erro: o sucesso continua no `toast`, o `fail()` de validação no `role="alert"` — e é o
mesmo parágrafo que agora mostra a falha de rede.

## 3. Os três caminhos do botão

| caminho | o que se mediu | botão |
| --- | --- | --- |
| **sucesso** (POST normal) | toast «Preferências guardadas.» | volta a «Guardar preferências», `disabled: false` |
| **excepção** (POST abortado) | `role="alert"`: «Não consegui ligar ao servidor — as preferências não foram guardadas. Verifica a ligação e tenta outra vez.» | `disabled: false`, e o `<form>` continua na página (`form` = 1) |
| **`fail()` de validação** | o `if (!resultado.ok) { setErro(…); return; }` fecha a transição e o `useTransition` volta a `pending: false` | `disabled: false` |

O caminho do `fail()` **não é alcançável pela interface** (o `Select` só oferece 1–28 e o regime é um
par fixo): o que se prova é o código — o `return` dentro do `try` deixa a transição terminar como o
caminho de sucesso, e é o mesmo `pending` que já se media na T97. Não inventei um formulário inválido
para o alcançar.

## 8. Volta 2 — o `try` ficou mínimo

O QA mediu: o `try` cobria o `await`, o `if (!resultado.ok)` **e** o `toast.success`. Assim, se o
`setErro` ou o `toast` lançassem um dia, o utilizador leria «Não consegui ligar ao servidor» **com o
servidor a ter respondido** — a mensagem a mentir sobre a causa, num ecrã que existe para dizer o que
ficou gravado.

```diff
+      let resultado: Awaited<ReturnType<typeof savePreferences>>;
+
       try {
-        const resultado = await savePreferences({ … });
-
-        if (!resultado.ok) {
-          setErro(resultado.error);
-          return;
-        }
-
-        toast.success('Preferências guardadas.');
+        resultado = await savePreferences({ … });
       } catch {
-        setErro('Não consegui ligar ao servidor — …');
+        setErro(
+          'Não consegui ligar ao servidor — as preferências não foram guardadas. Verifica a ligação e tenta outra vez.',
+        );
+        return;
       }
+
+      if (!resultado.ok) {
+        setErro(resultado.error);
+        return;
+      }
+
+      toast.success('Preferências guardadas.');
```

O `try` fecha **logo a seguir ao `await`**; o `if` do `fail()` e o `toast` do sucesso ficam fora, e cada
um falha com a sua própria consequência em vez de se disfarçar de erro de rede. O texto da mensagem não
mudou, nem a acção, nem o schema, nem o spec.

**Comportamento observável:** o mesmo — o `await` é o único ponto que pode rejeitar por rede; o `catch`

lançam: deixam de ser mascarados. **Não corri a suite** (o QA correu-a a 150 neste código, `0
