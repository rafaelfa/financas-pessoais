# T64 — `semCategoria` (e o par `valor`) no schema de filtros — prova do QA

**Veredicto: PASS nas seis alíneas**, na árvore final (com `semCategoria`, `valor` e `valorOp`
declarados). A armadilha está desarmada para **as três chaves** que o URL leva e não é — está
provado por execução, com e sem as linhas, e o controlo assere o **código** do erro.

## Volta 1 — o buraco que a primeira leitura não via

O Dev declarou só `semCategoria`. Eu executei o `strict()` com o objecto da página:

```
{ semCategoria:'1', valor:'100', valorOp:'gt', search:'mercado', limit:'25' } → true
```

Mas o teste dele só levava `semCategoria` e `search` — e o Revisor mostrou o que faltava: com o
objecto **completo**, `strict()` recusava `valor` e `valorOp` com `unrecognized_keys`. Ou seja, a
armadilha estava desarmada numa chave e armada nas outras duas: no dia em que alguém tornasse o
schema estrito, quem tivesse `?valor=100&valorOp=gt` perdia **todos** os filtros. Resposta ao ponto
7 do pedido: `valor`/`valorOp` **não** estavam legitimamente fora do schema — o parser validava a
semântica, mas o `safeParse` do objecto caía.

## Volta 2 — árvore final

### 1. A prova central (corrida por mim)

Com `transactionFiltersSchema.strict()` e o objecto completo que a página constrói:

```
$ npx tsx strict-check.ts          # árvore final (semCategoria + valor + valorOp declarados)
strict(completo).success = true
strict(chave inventada).success = false | codes = ["unrecognized_keys"]

# cópia sem as duas linhas `valor`/`valorOp`
strict(completo).success = false
issues = [{"code":"unrecognized_keys","keys":["valor","valorOp"]}]
strict(chave inventada).success = false | codes = ["unrecognized_keys"]
```

O objecto completo: `from`, `to`, `accountId`, `categoryId`, `kind`, `status`, `search`,
`semCategoria:'1'`, `valor:'100'`, `valorOp:'gt'`, `limit:'25'`, `offset:'50'`.

### 2. O controlo assere o código, não só o `success`

No teste (`transaction-filters.test.ts`), o último caso é:

```ts
const parsed = transactionFiltersSchema.strict().safeParse({ filtroInventado: '1' });
expect(parsed.success).toBe(false);
expect(parsed.error?.issues.map((issue) => issue.code)).toContain('unrecognized_keys');
```

Sem o código, um `success: false` por outro motivo qualquer também passaria — o teste fecha isso.

**O vermelho** (cópia sem a linha de `semCategoria`, build do pacote, teste do `shared`):

```
 × `semCategoria` é aceite e chega ao valor validado
 × só o valor `1` é aceite — o resto é recusado, não ignorado
 × um clone estrito do schema aceita o objecto **completo** que a página constrói
 ✓ e o clone estrito recusa uma chave que não existe, com `unrecognized_keys`
 Tests  3 failed | 1 passed (4)
 AssertionError: expected undefined to be '1' // Object.is equality
 AssertionError: expected true to be false // Object.is equality
 AssertionError: expected false to be true // Object.is equality
```

Falhas de **asserção** com mensagem, não erro de compilação. E sem as duas linhas `valor`/`valorOp`
(isoladas): **1 failed | 3 passed** — só o teste do objecto completo cai, que é o que se espera.
Ficheiros repostos: `git diff --numstat` → `apps/web/src/server/transactions.ts` **14+/3−**,
`packages/shared/src/schemas/domain/transactions.ts` **18+/0−**.

### 3. O comportamento não mudou

Cenário próprio (4 gastos: 10, 20, 30 sem categoria — o de 30 `PENDING` — e 40 categorizado):

| leitura | valor |
|---|---|
| cartão «Sem categoria» na Revisão | **3** |
| `/transacoes?semCategoria=1` | **total 3**, 3 linhas, chip «Sem categoria» visível |
| recarregar | mantém `?semCategoria=1` e o chip |
| remover o chip | URL sem parâmetro, **total 4** (a lista toda), chip fora |

### 4. Os outros filtros, incluindo o par do valor

| filtro | total |
|---|---|
| sem filtros | **4** |
| `?valor=15&valorOp=gt` | **3** (20, 30, 40) |
| `?semCategoria=1&valor=15&valorOp=gt` | **2** (20, 30) |
| `?semCategoria=1&status=pending` | **1** (o de 30) |
| `?semCategoria=1&search=mercado` | **1** |

Declarar `valor`/`valorOp` no schema **não mudou a semântica**: as chaves só passam a ser aceites;
quem valida formato, operador e coerência continua a ser o `parseAmountFilter` (com os testes dele:
euros com vírgula/ponto, módulo, metades em falta, operador inválido, int32).
