## 1. O localizador novo, e porquê

Antes (`e2e/support/ui.ts`):

```ts
return page.locator('form').filter({ hasText: 'Natureza' });
```

Depois:

```ts
return page.locator('form').filter({ has: page.getByLabel('Valor', { exact: true }) });
```

O «Natureza» saiu do `<form>` (passou a três botões — Gasto, Ganho, Transferência —
fora dele), por isso o `hasText` procurava um formulário que já não existe. O âmbito
passa a ser o **campo** `Valor`, que continua dentro do formulário e tem `label` ligada
por `htmlFor` (`transaction-quick-add.tsx:393`). É o único campo com o nome acessível
exatamente «Valor» na aplicação — os diálogos usam «Valor (€)» e as tabelas usam células,
não `label` — e o `has` é avaliado **dentro** de cada `form`, portanto não depende de
unicidade na página. Mantém-se a regra do ficheiro: nome acessível, não estrutura.

## 2. Outra causa da mesma falha: não havia sessão

Os três testes abriam `/transacoes` **sem sessão**: o `describe` limpa o `storageState`
(`test.use({ storageState: { cookies: [], origins: [] } })`) e o `beforeAll` só cria o
utilizador por HTTP — entrar pela interface estava escrito só no teste (c). Os outros
eram desviados para `/entrar` e esperavam 20 s pelo formulário numa página onde ele não
existe. Acrescentei um `test.beforeEach` que entra pela interface (o comentário do
`describe` já dizia «cada teste entra pela interface») e tirei a entrada duplicada do
teste (c).

## 5. Defeito de produto encontrado (não corrigido — fora do meu âmbito)

```
[F8.5] Editar → Estado «Por confirmar» → HTTP 500 · base CONFIRMED · aviso=false

⨯ Error: .partial() cannot be used on object schemas containing refinements
```

Origem: `apps/web/src/server/transactions-actions.ts:446-447` —

```ts
const parsed = createTransactionSchema
  .partial()
  .extend({ id: z.string().min(1) })
  .safeParse(input);
```

`createTransactionSchema` é um `superRefine(...)` (`packages/shared/src/schemas/domain/transactions.ts:75`).
No Zod 4, `.partial()` sobre um schema com refinamentos lança exatamente esse erro, e a
rota devolve 500. Consequência: **qualquer edição de lançamento pela interface falha**
(não só a mudança de estado). O schema de update já existe e não usa `.partial()`
(`updateTransactionSchema`, linha 147) — a correção é provavelmente passar a usá-lo, mas
é decisão do Dev.

É pré-existente e não foi introduzido por esta tarefa (o teste nunca chegava lá porque
morria antes, no localizador).
