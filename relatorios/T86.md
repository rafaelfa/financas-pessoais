# T86 — transferência: o modo abre com a conta de destino vazia

Data: 2026-11-22 · Base: `main` @ `3297aca` (T87)
Build medido: `BUILD_ID N561RXJqPeOUMQ3s8oH9s`, `next start` na 3000.

## 1. Diagnóstico (medido, não suposto)

**A hipótese das contas arquivadas morreu.** Com a conta demo — `Carteira principal`, `Conta
ordenado`, `Poupança`, **nenhuma arquivada** (`SELECT name, "archivedAt" FROM financial_account …` →
três linhas com `archivedAt: null`) — o inicializador das linhas 97-99 **produz um id válido**.
Registei o estado à saída do primeiro render:

```
[T86-state] {"toAccountId":"7475d75d-88db-4566-80ab-9c820d549890","accountId":"71de452d-…","n":3}
```

E logo a seguir, quando o `Select` de destino **monta** (o modo passa a Transferência):

```
[T86-sel-destino] ""
[T86-state] {"toAccountId":"","accountId":"71de452d-…","n":3}
[T86]  {"accountId":"71de452d-…","toAccountId":"","date":"2026-11-22","amountInCents":5000,…}
```

**Causa real:** o `Select` do Radix perde o valor porque a lista de `SelectItem` só é montada quando
o `SelectContent` abre. No `SelectBubbleInput` do próprio Radix
(`node_modules/.pnpm/@radix-ui+react-select@2.3…/dist/index.mjs`, ~1108-1135) há um efeito que, ao
mudar o valor, escreve no `<select>` nativo escondido **e dispara um `change`**; sem `<option>`
nenhuma, a escrita fica em `""` e o `change` chega ao `onValueChange` como `""`. O nosso
`onValueChange={setToAccountId}` aceitava esse `""` e apagava o destino. O `Select` da conta de
origem não dispara nada equivalente (não aparece nenhum log dele).

Consequência medida a seguir: `createTransferSchema.safeParse` falha em `entityIdSchema`
(`packages/shared/src/schemas/domain/primitives.ts:67`) e o formulário mostra «Falta o identificador.»
**sem fazer um único pedido de rede** (`posts: 0` capturados na página) — é validação de cliente, não
uma action a recusar.

Resposta à pergunta do Lead: é a pista **(b)** — estado inicial certo, valor perdido pelo componente;
não é `defaultAccountId` a devolver `''`.

## 2. Correção (mínima)

`apps/web/src/components/transaction-quick-add.tsx`, +15/−4: o destino passou a ser **derivado** em vez
de estado inicial fixo — o que o utilizador escolher ou, até escolher, a primeira conta **ativa** que
não é a de origem:

```diff
-  const [toAccountId, setToAccountId] = useState(
-    () => accounts.find((account) => account.id !== defaultAccountId(accounts))?.id ?? '',
-  );
+  const [chosenToAccountId, setChosenToAccountId] = useState('');
...
+  const toAccountId =
+    chosenToAccountId === ''
+      ? (activeAccounts.find((account) => account.id !== accountId)?.id ?? '')
+      : chosenToAccountId;
...
-                <Select value={toAccountId} onValueChange={setToAccountId}>
+                <Select value={toAccountId} onValueChange={setChosenToAccountId}>
```

Porque é a mínima: nenhum componente novo, nenhum `Select` diferente, nenhuma consulta, nenhuma
dependência; um estado que só guarda a escolha explícita e um valor efetivo calculado. O filtro passou
a ser sobre `activeAccounts`, por isso a hipótese original (conta arquivada como destino) também
deixa de ser possível. `needsTwoAccounts` e a mensagem existente não mudaram.
