## 2. A — dupla contagem (BLOQUEADO, com a correção pronta)

**Causa medida no código:** `GoalMovement.transaction` é `onDelete: SetNull` no esquema, e
`deleteTransaction` apaga só a transação:

```ts
// apps/web/src/server/transactions-actions.ts:641
await prisma.$transaction(async (tx) => {
  if (existing.transferGroupId !== null) { … }
  await tx.transaction.delete({ where: { id } });
});
```

O movimento do objetivo fica com `transactionId = null` e continua a somar no objetivo — o dinheiro volta
à conta e não sai do objetivo, que é exactamente os 183 708,55 € da varredura.

**A correção que verifiquei ser necessária** (uma chamada, dentro da mesma transação, antes do `delete`):

```ts
await tx.goalMovement.deleteMany({ where: { transactionId: id } });
```

**Porque não a apliquei:** `apps/web/src/server/transactions-actions.ts` não está na lista da T105. Não
escrevi fora da lista e não inventei um caminho alternativo (um `$extends` no cliente Prisma ou uma
limpeza no ecrã do objetivo seriam correções piores e fora do sítio). **O spec não foi escrito** porque um
spec que fica vermelho sem correção possível na minha mão não acrescenta prova — fica pronto para a volta
seguinte, com a lista a incluir esse ficheiro.

## 3. B — «Adquirido em» (`0001-01-05`)

**Antes (Lead, produção):** o campo abre com `0001-01-05` e grava-o.
**Nesta máquina, o campo já abria vazio** — medido no diálogo «Novo bem»:

```
[{ "tipo": "text",  "valor": "" }, …,
 { "tipo": "date", "valor": "", "id": "…-acquiredOn" },
 { "tipo": "date", "valor": "", "id": "…-valuedOn" }]
```

Não conseguindo reproduzir a origem, fechei a **classe** no diálogo (`asset-dialog.tsx`): qualquer data
fora de `AAAA-MM-DD` ou com ano < 1900 conta como «sem data», tanto ao abrir (valores iniciais) como ao
submeter. Uma data com ano 1 deixa de poder chegar ao servidor — que já convertia `undefined` em `null`
(`patrimonio-actions.ts:51`), por isso o registo fica sem data em vez de ficar no ano 1.

## 4. C — faturas por pagar

**Causa:** a cadeia de faturas transitа o que sobra para a seguinte, por isso **todas** as faturas de um
cartão têm `outstandingInCents > 0` enquanto a dívida existir. O Painel filtrava e **somava todas**
(12 faturas → 6 390 € na conta do Lead); a Revisão filtrava ainda por `status === 'closed'` (→ «Nenhuma»);
os Cartões mostram a **última** fatura (`server/cards.ts:69`, `lastInvoice`) → 0,00 € quando a última está
paga, mesmo com uma anterior em dívida.

**O que ficou na árvore:** uma regra só, em `server/invoice-context.ts` —

```ts
/** As faturas em dívida agora: uma por cartão, a mais antiga (a que se paga primeiro). */
export function invoicesInDebt(summaries) { … }
```

usada por:
- **`server/dashboard.ts`** (`unpaidInvoices`) — deixa de somar a cadeia;
- **`server/month-close.ts`** (`unpaid`, `unpaidTotal`) — o «Fechar o mês» só bloqueia se houver mesmo
  fatura por pagar;
- **`revisao/page.tsx`** (com `countInvoicesInDebt()`) — substitui a contagem que filtrava por `closed`.

**Medido nos ecrãs (demo, 1440×900):**

| ecrã | antes | depois |
| --- | --- | --- |
| Painel | «Faturas por pagar — **12** por resolver · **6390,00 €**» (na conta do Lead) / aqui a soma da cadeia | «Faturas por pagar — **1 por resolver · 412,30 €**» |
| Revisão | «**Nenhuma** fatura por pagar» | «**1 fatura por pagar**» |
| Cartões | «Em dívida: 0,00 €» | «Em dívida: **0,00 €**» — **continua a discordar** |

**O que falta, e onde:** `apps/web/src/server/cards.ts:69` usa `lastInvoice?.outstandingInCents ?? 0`; tem
de passar a usar a mesma regra (`invoicesInDebt`) para o cartão. Uma linha mais a importação:

```ts
const outstandingInCents = invoicesInDebt(invoices)[0]?.outstandingInCents ?? 0;
```

Sem essa linha os três ecrãs ainda não concordam — e é o único ponto de C que não está feito.

Reconciliação à mão do caso da varredura (o do Lead): 945 + 870 + 795 + 720 + 645 + 570 + 495 + 420 + 345
+ 270 + 195 + 120 = **6 390**; cada parcela inclui o transitado da anterior, logo a dívida real é a da
primeira em dívida (945). Com a regra nova, o Painel passaria a mostrar **1 · 945,00 €**.

### 9.4 B — o buraco que o QA mediu

Um bem que **já tem** `0001-01-05` na base perdia a correção porque o campo saía `undefined` e a ação de
edição não limpava nada. Agora:

```ts
function dataNormalizada(value: string | null | undefined): Date | null {
  if (value === null || value === undefined || !/^\d{4}-\d{2}-\d{2}$/.test(value)) {
    return null;
  }

  return Number(value.slice(0, 4)) >= 1900 ? new Date(value) : null;
}
```

Usado em `patrimonio-actions.ts:67-68` (criar) e `:110-111` (editar). Um registo com ano 1 perde-o ao ser
guardado, e um novo já não o pode receber. A prova ao vivo do registo semeado é do QA.

## 10. Volta 4 — o `null` do B no schema (`nullable()`)

**A regressão:** o diálogo passou a enviar `acquiredOn: null` e o schema era `calendarDateSchema.optional()`
— `.optional()` aceita `undefined`, **não** `null`. Um bem **sem data** (o caso normal) chegava ao
`createAsset` com `null`, o `safeParse` falhava e o formulário mostrava erro no campo «Adquirido em» em vez
de gravar.

**Medido no zod desta árvore:**

```
$ node --input-type=module -e "import {z} from 'zod'; const s=z.object({a:z.string().optional()});
  const n=z.object({a:z.string().nullable().optional()});
  console.log('sem nullable: null ->', s.safeParse({a:null}).success, '| undefined ->', s.safeParse({}).success);
  console.log('com nullable: null ->', n.safeParse({a:null}).success, '| undefined ->', n.safeParse({}).success)"
sem nullable: null -> false | undefined -> true
com nullable: null -> true | undefined -> true
```

**O contrato, em `packages/shared/src/schemas/domain/patrimonio.ts:45-46`:**

```ts
acquiredOn: calendarDateSchema.nullable().optional(),
valuedOn: calendarDateSchema.nullable().optional(),
```

Só no `assetShape`; o `liabilityShape` fica como está (não é desta tarefa). A ação já normaliza `null`
para `null` (`dataNormalizada`), por isso o registo sujo continua a ser limpo ao guardar.
