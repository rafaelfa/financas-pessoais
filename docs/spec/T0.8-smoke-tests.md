## 3. CSV — resultado esperado

Cabeçalho `Data;Descrição;Valor;Saldo`, 5 linhas de comentário (`#`) a ignorar. Saldo inicial 2.500,00 € (fora do ficheiro) para conferir a coluna `Saldo`.

| # | Data | Descrição | Valor | Cêntimos | Saldo (pt) |
|---|---|---|---|---|---|
| 1 | 01/10/2026 | Vencimento outubro | 2.150,00 | +215000 | 4.650,00 |
| 2 | 02/10/2026 | Renda casa outubro | -850,00 | -85000 | 3.800,00 |
| 3 | 05/10/2026 | Compra Continente; Matosinhos *(campo entre aspas com `;` dentro)* | -64,37 | -6437 | 3.735,63 |
| 4 | 06/10/2026 | Transferência recebida João Silva | 1.200,00 | +120000 | 4.935,63 |
| 5 | 08/10/2026 | Seguro automóvel | -312,45 | -31245 | 4.623,18 |
| 6 | 09/10/2026 | Levantamento multibanco | -50,00 | -5000 | 4.573,18 |

Aritmética (a regra de conversão é *tirar os pontos de milhar, trocar a vírgula por ponto, arredondar a 2 casas*):
`2150,00 → 215000` · `-850,00 → -85000` · `-64,37 → -6437` · `1200,00 → 120000` · `-312,45 → -31245` · `-50,00 → -5000`.
- **6 linhas**, soma dos valores = `215000 - 85000 - 6437 + 120000 - 31245 - 5000 = 207318` cêntimos = **+2 073,18 €**.
- Conferência cruzada da coluna `Saldo`: `2500,00 + 2073,18 = 4573,18` = último `Saldo` → coerente.
- **Sucesso** = 6 linhas, 4 colunas por linha, nenhuma coluna desalinhada na linha 6 (data `09/10/2026`, descrição `Levantamento multibanco`), e o registo 3 com a descrição completa `Compra Continente; Matosinhos` (o `;` entre aspas **não** pode partir o campo). Erros típicos a excluir: tratar `2.150,00` como `2,15`; ler datas como `mm/dd/aaaa`; contar as linhas `#` como dados.

## 4. OFX 1.x SGML vs OFX 2.x XML — diferenças práticas

| | OFX 1.x (SGML) | OFX 2.x (XML) |
|---|---|---|
| Versões | 1.0 a 1.6 — "Versions 1.0 through 1.6 relied on SGML for data exchange, while later versions are XML-based" ([Wikipedia](https://en.wikipedia.org/wiki/Open_Financial_Exchange)) | 2.0+ (última: Banking v2.3, [FDX/OFX Work Group](https://financialdataexchange.org/about-fdx/ofx-work-group/)) |
| Como se reconhece | primeiras linhas `OFXHEADER:100` + `DATA:OFXSGML` + `VERSION:102` ([PRONOM fmt/309](https://pronom.nationalarchives.gov.uk/fmt/309)) | `<?xml version="1.0" encoding="…"?>` + `<?OFX OFXHEADER="200" VERSION="211" …?>` e depois o elemento `<OFX>` |
| Cabeçalho | pares `CHAVE:VALOR`, um por linha, **antes** de `<OFX>`; campos `DATA`, `VERSION`, `SECURITY`, `ENCODING`, `CHARSET`, `COMPRESSION`, `OLDFILEUID`, `NEWFILEUID` (PRONOM) | atributos dentro da instrução de processamento `<?OFX …?>` — `OFXHEADER="200"`, `VERSION`, `SECURITY`, `OLDFILEUID`, `NEWFILEUID` |
| Tags de fecho | **ausentes nas tags de valor**; nos ficheiros reais, as tags de **bloco** (`STMTTRN`, `BANKTRANLIST`, `STATUS`, `STMTRS`, `OFX`) costumam estar fechadas | todas presentes (XML bem-formado) |
| Implicação para o parser | um parser XML puro **falha** (elemento sem fecho) → tem de haver normalização SGML→XML ou um lexer próprio | `fast-xml-parser`/`DOMParser`/`xml2js` servem, mas os nomes de campo colidem (ver I6 em §6) |
| Valores | texto simples, **sem aspas**, podendo conter `:` e `&`; o espaço em branco à volta do valor é ruído | texto XML com entidades (`&amp;`) |

**Amostra de evidência de como isto aparece na realidade** (e não como o estereótipo sugere): nos *fixtures* reais de OFX 1.x SGML do `ofx-js` ([example1.ofx](https://github.com/bradenmacdonald/ofx-js/blob/master/test/data/example1.ofx), Nova Zelândia) e do `ofx-data-extractor` ([example.ofx](https://github.com/Fabiopf02/ofx-data-extractor/blob/main/tests/example.ofx), banco brasileiro) as tags de bloco **estão** fechadas e só as tags de valor (`<TRNAMT>-24.90`, `<MEMO>…`) ficam abertas. As nossas amostras seguem esse estilo. A variante extrema — **zero** tags de fecho — é a incógnita I1 (§6), já parcialmente resolvida.

## 5. Veredicto sobre SGML nas bibliotecas candidatas

- **`ofx-js@1.1.2` — SUPORTA SGML 1.x e XML 2.x.** Código: existe uma função `sgml2Xml()` e o comentário "Try as XML first, and if that fails do the SGML->XML mangling" ([ofx.js, v1.1.2](https://unpkg.com/ofx-js@1.1.2/ofx.js)). Parser próprio (0 dependências) com validação de fecho. Os seus *fixtures* de teste incluem ficheiros SGML reais de bancos.
- **`ofx-data-extractor@1.5.0` — SUPORTA SGML 1.x e XML 2.x.** O *quick start* do próprio README usa um cabeçalho SGML (`OFXHEADER:100` / `DATA:OFXSGML` / `VERSION:102`) ([README v1.5.0](https://app.unpkg.com/ofx-data-extractor@1.5.0/files/README.md)) e o código trata explicitamente `<?xml`, `<?OFX` e `?>` ([bundle.min.js](https://unpkg.com/ofx-data-extractor@1.5.0/dist/umd/bundle.min.js)). Abordagem por regex + JSON, com `parserMode: 'strict' | 'lenient'`.
- **Ressalva — confirmada por réplica do código, já não é INFERÊNCIA.** "Suportam SGML" significa o SGML **como os bancos o exportam**, com as tags de bloco fechadas. Num OFX 1.x **sem nenhuma** tag de fecho (removidas as 22 linhas `</…>` do ficheiro principal), a via `sgml2Xml` do `ofx-js` atira `Missing closing tag for LEDGERBAL` (e a via XML estrita, `… for DTASOF`): a heurística do `sgml2Xml` só acrescenta fecho onde **há texto** a seguir à tag, logo uma tag de bloco vazia (`<LEDGERBAL>` seguida de outra tag) nunca é fechada. Como a segunda chamada do `parseSync` não está protegida por `try/catch`, o `parseStrict` **lança exceção** — não devolve dados errados, o que é preferível. O `ofx-data-extractor` procura literalmente `<STMTTRN>`…`</STMTTRN>` e não tem passo que acrescente fechos, pelo que também não cobre esse caso (por leitura do código; **não verificado a correr**).
- Consequência para o risco R8 do plano: passa de "nenhuma biblioteca confirma suporte" para **"as duas bibliotecas tratam OFX 1.x SGML no estilo exportado pelos bancos; falta provar com um extrato português real"**.

### Plano B — parser próprio do subconjunto SGML

Recomendado **só se I1 se confirmar num extrato real** (a variante extrema já se sabe que quebra as duas bibliotecas) e as bibliotecas falharem; caso contrário é trabalho a evitar. Ponto de partida: normalizar SGML→XML **antes** de entregar a qualquer parser XML, ou escrever um lexer de ~150–250 linhas.

Construções que teria de tratar:
1. **Tags de valor sem fecho** — `<MEMO>texto` termina no `<` seguinte ou no fim do ficheiro.
2. **Tags de bloco** que podem ou não estar fechadas (`</STMTTRN>`, `</BANKTRANLIST>`, `</OFX>`) → se a variante I1 existir, a estrutura **só** é recuperável com o esquema de tags (que tags são contentoras e fecham o pai); sem isso o resultado é uma árvore equilibrada mas errada.
3. **Valores sem aspas** que podem conter `:`, `,`, `&` e aspas (as amostras reais citadas têm `Repasse pagamento: 17223405 de …`).
4. **Quebras de linha** dentro e fora dos valores (ruído entre tags, `\r\n` de ficheiros Windows) e linhas em branco.
5. **Cabeçalho até à linha `<OFX>`** — ler pares `CHAVE:VALOR` até encontrar `<OFX>` (não assumir posição fixa; há ficheiros sem `COMPRESSION`), e ignorar comentários.
6. **Encoding** (I2) e normalização de `DTPOSTED` (`YYYYMMDDHHMMSS`, com ou sem `[fuso]`) e `TRNAMT` (ponto **ou** vírgula decimal).

Esforço honesto (INFERÊNCIA, 1 pessoa): **0,5 a 1 dia** para o caminho feliz das amostras + testes; **+0,5 dia** por cada construtor novo descoberto num extrato real (fuso, encoding, valores brasileiros). Só o ponto 2 (esquema de tags) exige uma tabela de hierarquia OFX mantida à mão — é o custo escondido do plano B e a razão para o adiar até haver evidência de I1.
